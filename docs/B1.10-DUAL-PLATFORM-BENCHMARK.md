# B1.10 — Dual-Platform Benchmarking and KPI Comparison

B1.10 adds an explicit paired experiment to the proven Tier-B controller. It
answers how the same canonical workload profile performs on Kubernetes and MN5;
it does not answer where a workload should be placed. Ordinary placement,
human review, override feasibility, cancellation, and orphan protection remain
on their existing path unless comparison mode is explicitly selected.

## Commands and execution semantics

The unified controller exposes two separate operational intents:

* `PLACEMENT` (the default) performs the established recommendation, operator
  approve/reject/override review, and execution of one approved target.
* `COMPARE` deliberately evaluates Kubernetes and MN5 and does not change the
  placement recommendation. In the interactive placement review, the existing
  `[A]`, `[R]`, `[O]`, and `[I]` actions are unchanged and `[C] Compare
  Kubernetes + MN5` is appended as an additional action. It delegates to the
  same comparison path as CLI `--mode COMPARE` and the `BOTH` alias.

The benchmark profiles are `synthetic-light-v1`,
`synthetic-heavy-common-v1`, and `synthetic-heavy-v1`.
`COMPARE` and its alias `BOTH` deliberately execute Kubernetes first and MN5
second. A failure on either platform is recorded and does not prevent the other
platform from running or the comparison report from being written.

```bash
./cloud-hpc synthetic-light-v1 --mode COMPARE
./cloud-hpc synthetic-heavy-common-v1 --mode COMPARE
./cloud-hpc synthetic-heavy-v1 --mode COMPARE
```

Comparison mode bypasses placement assessment and human placement review by
design: both targets are the experiment. Each experiment receives a `CMP-...`
parent identity and two ordered child execution identities. Both children carry
the same profile name and canonical profile/configuration SHA-256.

Comparison mode still reuses the established live B1 Kubernetes resource
assessment before workload submission. This supplies platform-feasibility
evidence without performing placement selection. If no eligible worker can
satisfy a profile, Kubernetes is recorded as `INFEASIBLE` /
`RESOURCE_INFEASIBLE` without creating a Job guaranteed to remain Pending; MN5
still runs and the comparison artifact is written. If a request passes the
assessment but later fails scheduling, available Pod `Unschedulable` details
are retained.

## Experimental matrix

| Experiment | Benchmark class | CPU | Kubernetes | MN5 | Purpose |
|---|---|---:|---|---|---|
| LIGHT | `LIGHT` | 4 | PASS | PASS | Direct performance comparison |
| HEAVY COMMON | `HEAVY_COMMON_FEASIBLE` | 8 | PASS | PASS | Direct heavy performance comparison |
| HEAVY CAPACITY | `HEAVY_CAPACITY_BOUND` | 16 | `RESOURCE_INFEASIBLE` | PASS | Capacity/placement-boundary evidence |

Common-heavy and capacity-heavy use the same synthetic-heavy experiment family,
seed (`20260813`), 400,000 training samples, 50,000 test samples, 256 features,
10 classes, 6 epochs, batch size 2048, model, and methodology. Only the
intentional CPU request/thread level differs: 8 versus 16. The canonical
16-CPU `synthetic-heavy-v1` remains a capacity probe. Its current Kubernetes
infeasibility is a cluster-capacity outcome, not a software failure. Memory
requests follow legitimate platform scheduler policies and are not claimed to
be equivalent allocations.

## KPI contract

The normalized model keeps queue wait (`start - submit`), execution runtime
(`end - start`), and end-to-end latency (`end - submit`) separate. It also
records scheduler state, success, exit code, failure reason, node/host,
requested and allocated resources, workload throughput and peak RSS where
available, and output integrity hashes where meaningful. Raw-hash matching and
semantic equivalence are `null` when either platform produced no result; the
report does not manufacture semantic mismatches against a missing output.

Kubernetes timestamps, status, node, exit code, and requests come from the Job,
Pod, and container status APIs. Workload KPIs come from workload output. Slurm
timestamps, state, exit code, allocation, node, requested memory, and MaxRSS are
normalized from the existing `sacct` query when returned. Every metric group
records provenance.

The reference HPC configuration assigns scheduler memory according to an
operator-supplied policy of 2 GB per requested workload CPU core: 4 requested cores imply 8 GB
(`8000M`), 8 imply 16 GB (`16000M`), and 16 imply 32 GB (`32000M`). The MN5
record preserves raw Slurm `ReqMem` as `scheduler_requested_memory` and records
the configured policy, expected memory, and whether the observation matches. This
calculation uses the workload profile's requested CPU, never Slurm
`AllocCPUS`. Kubernetes does not inherit this MN5 policy.

Scheduler requested/reserved memory and peak workload memory are distinct
measurements. Their values may differ, and cross-platform reports do not claim
equivalent memory reservations or alter validated workload requests to make
them equal.

Unsupported optional metrics are JSON `null`, CSV empty fields, and
`unavailable` in the Markdown summary. Metrics-server is not required. Energy
and monetary cost remain unavailable because B1 has no defensible common source
or cost model.

## Results

Results are written below `artifacts/benchmarks/<comparison-id>/`:

```text
workload.json
k8s/execution.json
k8s/metrics.json
mn5/execution.json
mn5/metrics.json
comparison.json
comparison.csv
summary.md
```

`comparison.json` is the complete machine-readable parent record;
`comparison.csv` has one analysis-friendly row per platform; and `summary.md`
contains individual KPI comparisons without declaring an overall winner.
Existing MN5 logs and retrieved results remain under `results/remote-jobs/`.

## Offline testing

```bash
python3 -m unittest discover -s tests -v
python3 -m py_compile src/benchmark_compare.py src/cloud_hpc.py src/run_pipeline.py
```

Tests inject fake Kubernetes inventory and Kubernetes/MN5 runners and never call
a real `kubectl`, SSH, or Slurm endpoint. They cover CLI recognition, the
unchanged default placement route, static infeasibility without Job submission,
continued MN5 execution, missing-output equivalence, profile invariants,
parent/child traceability, normalization, timing, partial failure, and reports.

## Known limitations

V1 is sequential only. Detailed live CPU utilization needs a future real
telemetry source. Slurm fields such as MaxRSS may be absent depending on site
accounting configuration. Energy and detailed CPU utilization remain
unavailable without a defensible common telemetry source. The final LIGHT,
HEAVY COMMON, and HEAVY CAPACITY matrix has been live validated; the memory
policy metadata and interactive COMPARE entry should be revalidated for each
site-specific deployment.
